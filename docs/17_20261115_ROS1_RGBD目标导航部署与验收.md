# ROS1 RGB-D 目标导航部署与验收

## 实车基线

- Jetson：`10.206.9.102`，ROS Melodic。
- 相机：Orbbec Astra Pro（USB `2bc5:0501` RGB、`2bc5:0403` depth）。
- 工作空间：`~/yahboomcar_ws`，叠加 `~/software/library_ws`。
- 导航：厂商 `yahboomcar_nav`、AMCL、map_server、move_base。
- 新包：`~/yahboomcar_ws/src/x3_target_navigation`。

2026-11-15 已完成编译，运行时只链接 OpenCV 4.1，核心 gtest 通过。
相机只读验收时，Astra RGB 驱动报告 `already-claimed interface` 后反复崩溃，
内核同时报告 `tegra-xusb Ring expansion failed`，`/dev/video0` 随后消失。
新包因此改为 OpenNI 仅启动 Astra 深度，RGB 由内核 UVC 和 `usb_cam`
发布，避免使用冲突的厂商 libuvc RGB 节点。

重新插拔后 `uvcvideo` 未自动绑定；在没有相机进程占用设备时重载一次
`uvcvideo` 后恢复 `/dev/video0`。随后已实测 RGB、注册深度和 RGB
CameraInfo 均为 640×480，frame 均为 `camera_rgb_optical_frame`。预览模式
确认服务正确拒绝执行，新节点没有 `/cmd_vel` 发布者。

当前 Jetson 的 OpenCV 4.1 CPU 推理约需 2.3–3.2 秒/帧。因此配置中的观测、
融合和任务新鲜度窗口按首版“静态唯一目标”放宽；它不满足动态目标连续追踪。

已确认演示地图是 2026-11-07 17:20 保存的 `final_site`，不是厂商 2022 年
附带的 `my_map`。地图已备份到本地，并以可移植相对路径部署为
`yahboomcar_nav/maps/final_site_20261107.{yaml,pgm}`。厂商导航 launch 原本
就支持 `map` 和 `use_rviz` 参数，因此无需修改底层导航代码。

联合只读验收已通过：地图为 800×800、0.05 m/像素，`/scan`、AMCL、
`map → camera_rgb_optical_frame` TF 和 `/move_base/make_plan` 均可用，
规划服务返回非空路径。新节点仍不发布 `/cmd_vel`，预览模式确认服务仍拒绝
执行；验收过程没有发送 move_base goal。

## 构建

```bash
source /opt/ros/melodic/setup.bash
source ~/yahboomcar_ws/devel/setup.bash
cd ~/yahboomcar_ws
catkin_make --pkg x3_target_navigation
catkin_make run_tests_x3_target_navigation
```

## 只读验收

先关闭会占用相机或串口的 MakerControl/Rosmaster GUI，设置
`ROBOT_TYPE=X3`，再通过新包统一启动，确保每个设备只有一个驱动：

```bash
export ROBOT_TYPE=X3
roslaunch x3_target_navigation target_navigation.launch \
  model_path:=$HOME/models/object_detection_yolox_2022nov_opencv41.onnx \
  start_bringup:=true \
  start_astra:=true \
  start_navigation:=true \
  map:=final_site_20261107 \
  execute:=false
```

```bash
rostopic type /camera/rgb/image_raw
rostopic type /camera/depth_registered/image_raw
rostopic type /camera/rgb/camera_info
rosrun tf tf_echo camera_rgb_optical_frame map
rostopic echo -n 1 /amcl_pose
rosservice call /move_base/make_plan \
  "start: {header: {frame_id: map}, pose: {orientation: {w: 1.0}}}
   goal: {header: {frame_id: map}, pose: {orientation: {w: 1.0}}}
   tolerance: 0.05"
```

上述检查只是接口检查；实际规划测试必须填写当前 AMCL 位姿附近的安全点。

观察 `/target_navigation/state`、`raw_target`、`fused_target` 和 `preview_goal`。
预览模式调用确认服务必须失败，且不应出现新增的 `/cmd_vel` 发布者。

## 短距执行门槛

必须同时满足：

1. 深度有效率、内参分辨率和时间戳稳定。
2. RGB、注册深度、CameraInfo 均使用 `camera_rgb_optical_frame`，且该
   frame 到 `map` 的 TF 在图像时间戳可查询。
3. 相机外参与人工测量一致。
4. AMCL 已在当前地图初始化，make_plan 返回可行路径。
5. 空旷场地、物理急停和现场看护到位。
6. 目标静止且画面中只有一个配置类别目标。

满足后才可使用 `execute:=true`，先核对预览目标，再执行：

```bash
rosservice call /target_navigation/confirm
```

首次候选净行程限制为 0.10 m。`SUCCEEDED` 后仍须通过新鲜视觉观测验证目标
漂移和停车距离；复核失败不能记作任务成功。
